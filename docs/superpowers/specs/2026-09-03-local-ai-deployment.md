# LifeOS Local AI Deployment Design

## Goal

Run LifeOS on `192.168.2.61` using the Qwen3.8 vision model at `192.168.2.11:8081`, add server-side web-search augmentation for meal parsing, and expose the existing CPU NeMo ASR model through an HTTP endpoint for voice meal logging.

## Constraints

- Do not interrupt the existing Home Assistant `llama-server` on `.61:8081`.
- Do not interrupt the existing TTS service on `.61:10201`.
- Do not load another NeMo model: `.61` already runs `nvidia/parakeet-tdt-0.6b-v2` through `wyoming-onnx-asr` at `.61:10300`.
- Keep ASR CPU-only; the host has a 6 GB GTX 1660 Ti and existing GPU workloads.
- LifeOS remains a single-admin Docker/Postgres deployment on `.61:3000`.

## Design

1. Add `infra/asr-http/server.py` to LifeOS and copy it to `/home/dogda/lifeos/infra/asr-http/server.py` beside the existing Wyoming ASR checkout. It accepts the raw request body at `POST /v1/audio/transcriptions` with any `audio/*` content type, enforces a 15 MiB limit, and runs `ffmpeg -nostdin -loglevel error -i pipe:0 -ar 16000 -ac 1 -f wav pipe:1`. It opens that WAV with Python's `wave` module and forwards only raw PCM frames (not the RIFF header) to Wyoming in this exact sequence: `Transcribe(language="en")`, `AudioStart(rate=16000,width=2,channels=1)`, `AudioChunk` frames from `wav_to_chunks(..., 1024)`, `AudioStop`, then reads until the first `Transcript`. English is intentional: the deployed LifeOS voice flow is English-only. It returns `{ "text": "..." }` when the transcript is non-empty; an empty transcript returns `422 {"error":"empty_transcript"}`. `GET /health` opens `127.0.0.1:10300` with a 2-second timeout and returns `{ "ok": true }`. A shared `ASR_HTTP_TOKEN` header protects both endpoints. Install `/home/dogda/.config/systemd/user/lifeos-asr-http.service` with `ExecStart=/home/dogda/wyoming-onnx-asr/.venv/bin/python /home/dogda/lifeos/infra/asr-http/server.py` and `EnvironmentFile=/home/dogda/lifeos/asr-http.env`; it binds `0.0.0.0:10202`, restarts on failure, and starts after networking. `ffmpeg` is installed as the only system package; `loginctl enable-linger dogda` makes the user service survive logout/reboot. The bridge's transcription request timeout is 45 seconds, leaving headroom in LifeOS's 60-second route.
2. Replace LifeOS's fal.ai client with a small OpenAI-compatible client using `LLAMA_CPP_BASE_URL=http://192.168.2.11:8081/v1` and a required `LLAMA_CPP_MODEL` set to the verified multimodal model id `/home/dogda/Documents/LLM_Runners/Qwen3.8-27B-Q3_K_M.gguf`. The client calls `/v1/models` once at first use only, finds the exact id in the standard `data[].id` list, finds its corresponding llama.cpp metadata entry in `models[]` by `name`/`model`/`id`, and requires that entry's `capabilities[]` contain `multimodal`; it never selects an arbitrary model. Text requests send `{ model, messages: [{role, content}], temperature, max_tokens, stream: false }` to `/chat/completions`; responses are read from `choices[0].message.content` and malformed/empty responses throw safe named errors. The replacement for `uploadLocal()` reads the local file, allows only existing JPEG/PNG/WebP files up to the existing 8 MiB upload limit, maps the extension to an explicit MIME type, and returns a `data:` URL. Vision sends an OpenAI content array containing the prompt and those data URLs, so no external image storage is required. `ai_messages` logging remains, with local model ids and endpoint metadata; image data URLs are redacted to `{image:mime,bytes}` in logs and audio bytes are never logged.
3. Implement a typed `searchWeb(query: string)` helper only where LifeOS already requests search (`/api/food/parse-meal`). `chatJson` accepts `webSearchQuery?: string`; the route passes the user's meal text. The helper sends only that bounded meal text, never the user id/profile, to DuckDuckGo HTML; it extracts at most five title/snippet/URL records, caps the context at 6,000 characters, and labels it as untrusted reference data. Search instructions/results are appended to the user prompt, never executed as model-provided code or URLs. Search runs once per `chatJson` call with a 5-second timeout; its prepared context is reused for the schema-repair retry. Search failure or zero results proceeds without context. The helper returns `{ context, used }`; `chatJson` stamps the schema's `search_used` field from that server-side value. The old `:online` suffix is removed.
4. Route `/api/food/transcribe` directly to `ASR_HTTP_URL` with `X-ASR-Token`, preserving the existing browser multipart input and `{ text }` response shape: LifeOS unwraps the `File` and forwards its raw bytes/content type to the bridge. `transcribeAudio` logs only endpoint/model metadata in `ai_messages` and never audio content. Remove the fal upload/transcription dependency from this path; English is passed explicitly to the bridge.
5. Remove the unused fal client/storage integration from the local deployment path, update `package.json`/lockfile, `next.config.ts`, `.env.example`, `docker-compose.yml`, `README.md`, `SECURITY.md`, and relevant `CONTRIBUTING.md` setup text, and document the local AI, ASR bridge, web search, first login, service URLs, token provisioning, and health checks. The `demo/` tree intentionally remains a static mock/demo and is not part of the deployed app. No `FAL_KEY` is required.

## Concrete interfaces and deployment

- LifeOS environment: `LLAMA_CPP_BASE_URL` (default `http://192.168.2.11:8081/v1`), `LLAMA_CPP_MODEL` (required in deployment and must equal the verified Qwen id), `ASR_HTTP_URL` (default `http://192.168.2.61:10202`), and `ASR_HTTP_TOKEN` (required). The Docker container uses these values verbatim.
- The bridge's token is generated once with `openssl rand -hex 32`, stored as `ASR_HTTP_TOKEN=...` in `/home/dogda/lifeos/asr-http.env` with mode 600, and copied only into LifeOS's uncommitted `.env`; it is never committed or printed in logs. The bridge reads the same file through its systemd `EnvironmentFile`.
- Bridge success/error bodies are JSON and never include upstream stack traces: `400 {"error":"empty_audio"}`, `401 {"error":"unauthorized"}`, `404 {"error":"not_found"}`, `413 {"error":"too_large"}`, `415 {"error":"unsupported_audio"}`, `422 {"error":"empty_transcript"}`, `502 {"error":"wyoming_failed"}` for a connected backend that drops/errors during transcription, `503 {"error":"wyoming_unavailable"}` for a failed preflight/connect, and `504 {"error":"transcription_timeout"}` after 45 seconds. LifeOS maps bridge 401/404/422 to HTTP 502 with `asr_invalid_response`, bridge 503/504 to HTTP 503 with `asr_unavailable`, and bridge 400/413/415/502 to HTTP 502 with `asr_invalid_response`, while preserving its existing `transcribe_failed` key; it logs only the status/error class locally.
- LifeOS local-AI client errors have exact codes: `local_ai_unavailable` for network timeout, model-list failure, or missing configured model (route HTTP 503); `local_ai_upstream_error` for a non-2xx completion response (route HTTP 502); `local_ai_invalid_response` for malformed/empty completion content (route HTTP 502); and `local_ai_invalid_json` after the schema retry fails (route HTTP 502). Routes preserve their existing error keys (`estimate_failed`, `parse_failed`, etc.); full upstream response bodies are not returned to browsers.
- The bridge binds to `0.0.0.0` because the LifeOS container reaches the host through `192.168.2.61`; the token is required even on the LAN. If UFW is active, allow TCP 10202 only from `192.168.2.0/24`. Existing `.61:8081`, `.61:10201`, `.61:10300`, and the Home Assistant systemd unit are read-only dependencies and are not restarted or reconfigured.

## Contracts

| Component | Request | Success | Failure/limits |
|---|---|---|---|
| ASR bridge `GET /health` | `X-ASR-Token` | `200 {"ok":true}` | `401` bad token, `503` Wyoming unavailable |
| ASR bridge `POST /v1/audio/transcriptions` | raw `audio/*` body, `X-ASR-Token`, max 15 MiB | `200 {"text":"..."}` | `400` empty, `401` bad token, `413` too large, `415` ffmpeg cannot decode, `422 {"error":"empty_transcript"}`, `502` connected Wyoming failure, `503` Wyoming unavailable, `504` timeout |
| llama.cpp `/v1/models` | no auth, 5-second timeout | exact `data[].id` is present and its matching `models[]` metadata has `capabilities[]` containing `multimodal`; validation cached for process lifetime | `local_ai_unavailable`/HTTP 503 if timed out, unreachable, or id absent; `local_ai_invalid_response`/HTTP 502 if matching metadata/capability is absent |
| llama.cpp `/v1/chat/completions` | OpenAI messages JSON, 20-second request timeout per call, `stream:false` | first choice message text | non-2xx → `local_ai_upstream_error`/HTTP 502; timeout/network → `local_ai_unavailable`/HTTP 503; malformed/empty → `local_ai_invalid_response`/HTTP 502 |

The ASR bridge binds to all interfaces because the LifeOS container reaches the host through `192.168.2.61`; the token is required even on the LAN. The bridge does not log audio bytes, deletes conversion buffers/files after each request, and serializes no new model work—the existing Wyoming handler's model lock remains authoritative. The concrete unit setup is: create the mode-600 environment file, install the unit, run `systemctl --user daemon-reload`, `systemctl --user enable --now lifeos-asr-http.service`, and run `sudo loginctl enable-linger dogda` once. The 45-second ASR timeout and 5-second search timeout leave route overhead; meal parsing performs at most one search plus two 20-second local-LLM calls within its existing 60-second budget.

## Failure behavior

- Missing local LLM or ASR endpoint returns the existing JSON error response from the relevant LifeOS route; ASR fetches have a 45-second timeout and each LLM call has a 20-second timeout. Meal parsing performs at most one 5-second search, one 5-second first-use model-list validation, plus two 20-second local-LLM calls (50 seconds worst case), leaving 10 seconds of route overhead within its existing 60-second budget.
- Search failure, zero results, or timeout does not fail meal parsing; parsing proceeds without search context and the server records `search_used: false`. A successful search requires at least one parsed result and sets it true.
- Audio larger than the existing 15 MB limit is rejected before forwarding; ffmpeg, Wyoming disconnects, empty transcripts, and malformed model responses produce bounded errors instead of hanging.
- Vision rejects unsupported/missing local files before calling the LLM with `local_ai_invalid_response`/HTTP 502; local model/model-list failures, unsupported multimodal responses, and schema-retry exhaustion are surfaced as safe AI errors.
- The ASR bridge rejects non-POST/unknown paths and limits request size.

## Acceptance checks

- `GET http://192.168.2.61:10202/health` with the token returns HTTP 200; a missing token returns 401; an unknown path returns 404.
- A short WAV and a browser-style WebM sent to the bridge return non-empty English text; empty audio returns 400; an oversized body returns 413; an undecodable body returns 415; an empty transcript returns 422; a Wyoming mid-request failure returns 502; an unavailable backend returns 503; and a timeout returns 504 without hanging.
- `systemctl --user is-enabled lifeos-asr-http.service`, `loginctl show-user dogda -p Linger`, and a service restart confirm persistent lifecycle without changing the existing ASR, TTS, or Home Assistant units.
- `GET http://192.168.2.11:8081/v1/models` is reachable from `.61`, contains the configured exact multimodal id, and a text completion succeeds; a model-list timeout/unreachable/id mismatch returns `local_ai_unavailable`/503, missing matching metadata/capability returns `local_ai_invalid_response`/502, an upstream completion error returns `local_ai_upstream_error`/502, a malformed/empty completion returns `local_ai_invalid_response`/502, and schema-retry exhaustion returns `local_ai_invalid_json`/502.
- A local image reaches the vision request as the correct data URL MIME type, its payload is redacted in `ai_messages`, and it returns parseable `FoodVisionSchema` JSON.
- Missing/unsupported vision input and a model-list response without multimodal capability fail with `local_ai_invalid_response`/HTTP 502 without persisting image bytes.
- Meal parsing succeeds with search results and also succeeds when the search request is forced to fail, with server-owned `search_used` true/false respectively.
- Meal plan, workout-program, weekly-insights, and food-photo routes use the local client and preserve their current JSON schemas.
- Authenticated `POST /api/food/transcribe` tests with multipart `audio` verify success forwarding and each bridge failure mapping: 401/404/422 → LifeOS 502 `asr_invalid_response`, 503/504 → LifeOS 503 `asr_unavailable`, and 400/413/415/502 → LifeOS 502 `asr_invalid_response`; all preserve `{text}` on success and `transcribe_failed` on failure, and leave no audio/image data URL in `ai_messages`.
- LifeOS build/typecheck pass without `FAL_KEY`.
- LifeOS starts at `http://192.168.2.61:3000`, database migrations/bootstrap complete, and authenticated voice meal transcription reaches the local ASR bridge.
